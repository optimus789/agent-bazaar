## WP12 provider-arc Postgres persistence
- 2026-09-07: unlike Hedera, Arc/Circle Nanopayments genuinely have no external, chain-native source of truth for individual payments before a batch settles (`GatewayClient` exposes only `getBalances()`, confirmed via the SDK's own `.d.ts`) — so `/seller`'s payment list can only ever be as durable as `provider-arc`'s own record of it. Checked the official reference implementation (github.com/circlefin/arc-nanopayments): it hits this exact same limitation and solves it the same way — persisting payment records to Postgres (Supabase, in their case).
- Added `PostgresLedger` (`apps/provider-arc/src/earnings.ts`), used automatically when `DATABASE_URL` is set; auto-creates its own table (`provider_arc_payments`) on first connect, loads existing rows into memory at boot, and persists every new payment. Falls back to the original in-memory + JSONL `Ledger` when `DATABASE_URL` is unset — local dev, tests, and `MOCK=1` are unaffected. A DB write failure is logged and degrades gracefully (the in-memory record and JSONL line still succeed) rather than failing the live request.
- Provisioned a real Railway Postgres service in the same project; `provider-arc` connects over Railway's internal private network (`postgres.railway.internal`) — no public exposure, no meaningful egress cost (internal service-to-service traffic isn't billed as egress on Railway).
- 4 new tests (mocked `pg.Pool`, no real DB needed for CI): loads existing rows on connect, persists new records with the correct SQL params, and degrades gracefully on a DB write failure without losing the in-memory/JSONL record. `pnpm -r typecheck && pnpm -r test` green (109 tests).
- Verified against the real, live Railway deployment: made one real Arc nanopayment against `https://provider-arc-production.up.railway.app`, confirmed it appeared in `/v1/seller/earnings` immediately. Redeploy-survival check in progress — see next entry once confirmed.
